# Воспроизведение багов `sand_ordered`

Четыре истории про то, что случается с упорядоченным списком, в который писали два
разных аккаунта. Разбор — в `bog/articles/issue-sand-ordered.md`.

```sh
npx mam giper/baza/repro                       # собрать
node giper/baza/repro/-/node.js                # все сюжеты, ~5 с
node giper/baza/repro/-/node.js story=solo     # solo | pair | cycle | root
```

Запускать `npx mam` только из корня воркспейса: из подпапки он склонирует воркспейс туда.

| сюжет | что показывает |
| :- | :- |
| `solo` | одному пиру достаточно одной чужой записи, чтобы его собственная перестановка потеряла элемент |
| `pair` | два пира правят по очереди — обе реплики сходятся на одном и том же битом списке |
| `cycle` | пешка перестаёт читаться совсем: обход в конце `sand_ordered` не заканчивается |
| `root` | один `self` от двух пиров и разница между ключом по `self` и ключом по `path()` |

Конкурентности нет ни в одном сюжете: пиры ходят по очереди, после каждого шага
идёт полный обмен юнитами в обе стороны.

Ключи зашиты в `repro.node.ts` намеренно: исход зависит от лексикографики Lord'ов, и с
фиксированной парой он повторяется побайтово от прогона к прогону. Проигрывает пир с
меньшим Lord'ом, так что `A` здесь заведомо потерпевший. Сами `self` в сюжете `root`
каждый раз новые — ленд при создании получает случайную область, — но какая запись
вытесняет какую, не меняется.

`cycle` оставляет пешку нечитаемой, поэтому общий прогон запускает его отдельным
процессом с таймаутом в минуту. В зависимости от того, во что упрётся V8, он либо
падает с `RangeError` изнутри `sand_ordered`, либо не заканчивается вовсе — сюжет
сообщает и то, и другое.
